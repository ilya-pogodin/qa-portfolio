# Шаблон тест-кейса

Этот файл показывает, как устроены остальные файлы в папке. Начните с него.

---

## Структура кейса

| Поле | Что писать |
|---|---|
| **ID** | TC-XXX-01. Префикс по объекту, номер по порядку |
| **Название** | Что именно проверяем — одной строкой, по делу |
| **Приоритет** | High / Medium / Low |
| **Тип** | Позитивный (всё правильно) / Негативный (ломаем специально) |
| **Предусловия** | Что должно быть выполнено до первого шага |
| **Тестовые данные** | Конкретные значения, которые используются в шагах |
| **Шаги** | Нумерованный список действий, одно действие — один шаг |
| **Ожидаемый результат** | Что должно произойти — проверяемо и однозначно |

---

## Пример

### TC-DEMO-01 — Вход с верными логином и паролем

**Приоритет:** High · **Тип:** позитивный

**Предусловия:** учётная запись создана и активна.

**Тестовые данные**

| Поле | Значение |
|---|---|
| Логин | test@example.com |
| Пароль | Test12345 |

**Шаги**

1. Открыть браузер и перейти по адресу тестового стенда.
2. Нажать кнопку «Войти» в правом верхнем углу.
3. В поле «Электронная почта» ввести `test@example.com`.
4. В поле «Пароль» ввести `Test12345`.
5. Нажать кнопку «Войти».

**Ожидаемый результат**

1. Происходит переход на главную страницу личного кабинета.
2. В правом верхнем углу отображается имя пользователя.
3. Сообщений об ошибке нет.

## Правила оформления

**Название** — из него должно быть понятно, что проверяется, без чтения шагов. «Создание платежа с валидными данными», а не «Проверка платежа».

**Шаги** — атомарные и воспроизводимые. Один шаг — одно действие. Человек, который видит систему впервые, должен пройти по ним без вопросов: где нажать, что ввести, куда смотреть.

**Ожидаемый результат** — формулировка, которую нельзя трактовать двояко. «Возвращается код 201 и тело с полями id, status, paymentUrl», а не «платёж создаётся».

**Негативные кейсы** — половина работы. На каждый позитивный сценарий приходится несколько негативных: пустые поля, невалидные типы, превышение границ, отсутствие авторизации, повторный запрос.

**Восстановление состояния.** Если кейс меняет настройки или данные, последним шагом должно идти возвращение к исходному состоянию. Иначе следующие кейсы упадут по чужой причине.

---

## Что делать, если ожидаемый результат неизвестен

Бывает, что требование не описано и зафиксировать ожидаемый результат нечем. Тогда кейс помечается как **заблокированный**: в него записывается, какой информации не хватает, и заводится вопрос к аналитику.

Придумывать ожидаемый результат в такой ситуации нельзя. Выполнение кейса с выдуманным требованием ничего не доказывает: любой результат нельзя назвать ни правильным, ни ошибочным.

## Набор кейсов для одного эндпоинта

Минимальный состав, от которого стоит отталкиваться:

- позитивный сценарий, всё валидно
- граничные значения: минимум, максимум, минимум−1, максимум+1
- невалидные типы данных
- обязательные поля отсутствуют
- нет авторизации или невалидный токен
- повторный запрос, если метод должен быть идемпотентным
