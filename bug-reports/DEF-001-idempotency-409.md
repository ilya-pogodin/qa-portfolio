# DEF-001 — Противоречие между идемпотентностью и кодом 409

**Тип:** дефект требований (найден при статическом тестировании спецификации)
**Документ:** ZooTicket Payments API, openapi.yaml v1.1.0
**Раздел:** `POST /payments`
**Severity:** Major
**Priority:** High
**Дата:** 22.09.2026
**Статус:** открыт, направлен аналитику

---

## Описание

Спецификация описывает поведение при повторном запросе двумя способами, и они противоречат друг другу.

В описании заголовка `Idempotency-Key` сказано, что повторный запрос с тем же ключом не создаёт новый платёж, а возвращает уже созданный.

В перечне ответов для того же метода указан код `409 Conflict` с ошибкой `payment_already_exists` и сообщением о том, что платёж по этому заказу уже создан.

Из документа невозможно понять, что вернёт сервис при повторном нажатии кнопки «Оплатить»: ранее созданный платёж с кодом 201 или ошибку 409.

## Почему это важно

Это основной сценарий, ради которого идемпотентность и вводилась. Если фронтенд ожидает 201 с данными платежа, а получает 409, пользователь увидит ошибку при совершенно нормальном действии — повторном нажатии кнопки на медленном интернете.

Кроме того, из-за неопределённости невозможно зафиксировать ожидаемый результат в тест-кейсе TC-PAY-03: сейчас он заблокирован.

## Вопросы к аналитику

1. Что возвращается при повторном запросе с тем же ключом и тем же телом: 201 с существующим платежом или 200?
2. В каком случае тогда срабатывает 409 — только при совпадении `orderId` при разных ключах идемпотентности?
3. Что происходит при совпадении ключа, но изменившемся теле запроса? В платёжных API это обычно 422, но в спецификации такого ответа у метода нет.
4. Есть ли у ключа идемпотентности срок жизни?

## Предлагаемая правка

Развести два сценария явно: повторный запрос с тем же ключом → возврат ранее созданного платежа; конфликт по `orderId` при другом ключе → 409. Добавить ответ 422 для случая «ключ тот же, тело другое».
