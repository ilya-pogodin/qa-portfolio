# POST /payments — создание платежа

**Объект:** ZooTicket Payments API v1.1.0
**Метод:** `POST /payments`
**Спецификация:** [openapi.yaml](https://github.com/ilya-pogodin/data-analytics-portfolio/blob/main/systems-analysis/zooticket/openapi.yaml)
**Дата составления:** 22.09.2026

**Техники тест-дизайна:** эквивалентное разбиение, граничные значения, таблица решений для идемпотентности.

---

## Что понадобится

| Что | Где взять |
|---|---|
| Postman | postman.com, бесплатной версии достаточно |
| Коллекция запросов | [zooticket.postman_collection.json](../api-testing/zooticket.postman_collection.json) |
| Адрес тестового стенда | у разработчика |
| Токен авторизации | у разработчика, выдаётся на тестовый аккаунт |

## Подготовка (выполняется один раз перед всеми кейсами)

1. Установить Postman и открыть его.
2. Импортировать коллекцию: **File → Import**, перетащить файл `zooticket.postman_collection.json`.
3. Открыть коллекцию, вкладка **Variables**. Заполнить `baseUrl` (адрес стенда) и `token`. Нажать **Save**.
4. Записать номер проверяемой сборки — понадобится при заведении дефекта.

**Где смотреть результат.** После нажатия **Send** внизу открывается панель ответа: код ответа — справа сверху рядом со временем выполнения, тело ответа — на вкладке **Body**, результаты автоматических проверок — на вкладке **Test Results**.

## Общие предусловия

Если в кейсе не сказано иное, действуют для всех: подготовка выполнена, стенд доступен, токен действителен.

## TC-PAY-01 — Создание платежа с валидными данными

**Приоритет:** High · **Тип:** позитивный

**Тестовые данные**

| Поле | Значение |
|---|---|
| Idempotency-Key (заголовок) | key-001 |
| orderId | 1024 |
| amount | 1500 |
| currency | RUB |
| returnUrl | https://zooticket.ru/success |

**Шаги**

1. В Postman открыть запрос «01. Создание платежа — валидные данные».
2. Перейти на вкладку **Headers** и убедиться, что заголовок `Idempotency-Key` имеет значение `key-001`.
3. Перейти на вкладку **Body** и сверить тело запроса с таблицей тестовых данных.
4. Нажать **Send**.
5. Посмотреть код ответа и содержимое вкладки **Body** в панели ответа.

**Ожидаемый результат**

1. Код ответа — 201.
2. В теле ответа присутствуют поля `id`, `status`, `paymentUrl`.
3. Значение `status` равно `pending`.
4. Значение `paymentUrl` — ссылка вида `https://...`, открывается в браузере.

## TC-PAY-02 — Повторный запрос с тем же ключом идемпотентности

**Приоритет:** High · **Тип:** позитивный

**Предусловия:** выполнен TC-PAY-01, значение `id` из его ответа записано.

**Шаги**

1. Открыть запрос «02. Повтор с тем же ключом идемпотентности».
2. Убедиться, что заголовок `Idempotency-Key` равен `key-001` — тому же, что в TC-PAY-01.
3. Убедиться, что тело запроса полностью совпадает с телом из TC-PAY-01.
4. Нажать **Send**.
5. Сравнить значение `id` в ответе с записанным в TC-PAY-01.

**Ожидаемый результат**

1. Новый платёж не создаётся.
2. Значение `id` в ответе совпадает со значением из TC-PAY-01.

## TC-PAY-03 — Тот же ключ, изменённое тело запроса

**Приоритет:** High · **Тип:** негативный
**Статус: заблокирован** — ожидаемый результат зафиксировать нельзя, см. раздел «Заметки».

**Предусловия:** выполнен TC-PAY-01.

**Шаги**

1. Открыть запрос «01. Создание платежа — валидные данные».
2. На вкладке **Headers** оставить `Idempotency-Key` равным `key-001`.
3. На вкладке **Body** изменить значение `amount` с `1500` на `2000`.
4. Нажать **Send**.
5. Зафиксировать код ответа и тело.

**Ожидаемый результат**

Не определён. В спецификации поведение не описано. Типовое решение платёжных API — код 422 с указанием, что ключ уже использован с другими параметрами, но требовать этого нельзя, пока не уточнено. Фактический результат зафиксировать и передать аналитику вместе с [DEF-001](../defect-reports/DEF-001-idempotency-409.md).

## TC-PAY-05 — Сумма равна нулю

**Приоритет:** High · **Тип:** негативный
**Техника:** граничные значения
**Статус:** заблокирован — требование не определено ([DEF-002](../defect-reports/DEF-002-amount-validation.md))

**Требование:** в спецификации нет `minimum` для `amount`, поэтому допустимость нулевой суммы не определена.

**Цель проверки:** зафиксировать фактическое поведение системы при `amount: 0` и передать его аналитику для решения, принимать ли такую сумму.

**Шаги**

1. Открыть запрос «03. Создание платежа — нулевая сумма».
2. На вкладке **Body** проверить, что `\"amount\": 0`.
3. Убедиться, что `Idempotency-Key` отличается от использованных ранее — иначе сработает идемпотентность и вернётся старый платёж.
4. Нажать **Send**.
5. Записать код ответа и значение поля `code` (если есть) в раздел «Фактический результат».

**Фактический результат:** _заполнить при прогоне_

**Ожидаемый результат:** не определён по требованиям. Станет известен после ответа аналитика на вопрос о минимальной сумме.

## TC-PAY-06 — Отрицательная сумма

**Приоритет:** High · **Тип:** негативный
**Статус:** заблокирован — требование не определено ([DEF-002](../defect-reports/DEF-002-amount-validation.md))

**Требование:** в спецификации не указано, допустима ли отрицательная сумма. Тип `number` её не исключает.

**Цель проверки:** зафиксировать, отклоняет ли система `amount: -500`, и с каким кодом и сообщением, для передачи аналитику.

**Шаги**

3. На вкладке **Headers** задать новое значение `Idempotency-Key`, например `key-neg`.
4. Нажать **Send**.
5. Записать код ответа, поле `code` и текст `message` в раздел «Фактический результат».

**Фактический результат:** _заполнить при прогоне_

**Ожидаемый результат:** не определён по требованиям. Если система создала платёж с отрицательной суммой — это зафиксированное поведение, которое нужно обсудить с аналитиком как потенциальный дефект.

## TC-PAY-07 — Дробная сумма

**Приоритет:** Medium · **Тип:** негативный
**Статус:** заблокирован — требование не определено ([DEF-002](../defect-reports/DEF-002-amount-validation.md))

**Требование:** не определено. В спецификации не указано, в рублях или копейках передаётся `amount`, и сколько знаков после запятой допустимо.

**Цель проверки:** зафиксировать, как система обрабатывает дробную сумму (округляет, отбрасывает или передаёт как есть), и выявить расхождение между суммой в запросе и суммой на странице оплаты.

**Шаги**

1. Открыть запрос «01. Создание платежа — валидные данные».
2. На вкладке **Body** изменить `\"amount\"` на `1500.55`.
3. Задать новый `Idempotency-Key`, например `key-frac`.
4. Нажать **Send**.
5. Если платёж создан — открыть `paymentUrl` и записать сумму, которая отображается на странице оплаты.

**Фактический результат:** _заполнить при прогоне_

**Ожидаемый результат:** не определён по требованиям. Расхождение между суммой в запросе и на странице оплаты фиксируем как наблюдение для аналитика; вывод о дефекте делаем только после уточнения единиц измерения.

## Заметки

**Про TC-PAY-03.** Кейс намеренно оставлен без зафиксированного ожидаемого результата. Пока требование не уточнено, любой результат нельзя назвать ни правильным, ни ошибочным — выполнение такого кейса не подтверждает качество.

**Про границы.** Полноценных кейсов на граничные значения суммы здесь нет: в спецификации не заданы ни минимум, ни максимум. После того как ограничения появятся, добавить четыре кейса — на `min−1`, `min`, `max`, `max+1`.

**Про ключи идемпотентности.** В каждом кейсе, где создаётся новый платёж, значение `Idempotency-Key` должно отличаться от использованных ранее. Иначе сервис вернёт ранее созданный платёж, и кейс проверит не то, что задумано. Это частая ошибка при первом прогоне.
