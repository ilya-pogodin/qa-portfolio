# Прогон 2 — результаты

**Дата:** 27.09.2026
**Окружение:** macOS, Node.js v24.21.0, npm 11.19.0
**Объект:** MCP-сервер, сгенерированный SwaggerHub по OpenAPI-спецификации
**Метод:** ручная отправка запросов через curl

**Отличие от прогона 1.** Запущена локальная заглушка API на порту 4001, MCP-сервер стартовал с переменной `MCP_API_URL=http://localhost:4001`. Внешний API доступен и отвечает корректно — то есть впервые проверен успешный сценарий работы инструментов.

## Главный результат

**Инструменты ломаются именно на успешном сценарии.**

Наиболее наглядно это видно на паре запросов подряд:

| Запрос | Результат |
|---|---|
| `get-product` с `productId: "p1"` — товар существует | ошибка протокола −32602, данные не приходят |
| `get-product` с `productId: "p99"` — товара нет | `{"type":"text","text":"Failed to retrieve product data"}` |

Когда API возвращает данные, инструмент формирует ответ с типом содержимого `json`, которого нет в спецификации MCP, и SDK отклоняет результат. Когда данных нет, срабатывает ветка обработки ошибки с типом `text` — формально корректная.

Подробности в [BUG-005](BUG-005-invalid-content-type.md).

Это объясняет, почему в прогоне 1 дефект не проявился: при недоступном API все вызовы шли по ветке ошибки.

## Второй дефект

`delete-product` сообщил «Failed to delete product», тогда как API на то же действие отвечает кодом 204 — успехом.

Проверено прямым запросом к API в обход MCP-сервера:

```
curl -i -X DELETE http://localhost:4001/products/p1
HTTP/1.1 204 No Content
```

Причина в безусловном разборе тела ответа, которого у кода 204 нет. Подробности в [BUG-006](BUG-006-delete-reports-false-failure.md).

## Подтверждено из прогона 1

**Отсутствие описания у `echo`** — повторно видно в ответе `tools/list`, состав полей не изменился.

**Неработающий скрипт из комплекта** — `mcp.list_capabilities` снова вернул −32601.

**Неразличимость ошибок** — подтверждается косвенно: `get-product` с несуществующим товаром вернул тот же текст «Failed to retrieve product data», что и в прогоне 1 при полностью недоступном API. Причины разные, сообщение одинаковое.

## Что работает

**Валидация входных данных.** `add-product` без поля `price` отклонён с подробным указанием пути и ожидаемого типа. Результат совпадает с прогоном 1.

**Инструмент `echo`.** Возвращает корректный ответ, кириллица не искажается.

**Обработка отсутствующих данных.** Запрос несуществующего товара не роняет сервер и не приводит к ошибке протокола.

## Что осталось непроверенным

**Заказы.** Ни один из пяти инструментов — `get-orders`, `create-order`, `get-order`, `update-order`, `delete-order` — не вызывался. С высокой вероятностью поведение повторяет товары: код сформирован одинаково. Но это предположение, а не результат проверки.

**Обновление.** `update-product` не вызывался.

**Коды ответов 4xx и 5xx от внешнего API.** Заглушка отдаёт только 200, 201, 204 и 404. Поведение при ошибке 500 на стороне API не проверялось.

**Детализация уязвимостей.** Команда `npm audit` не выполнялась, состав проблем из [BUG-004](BUG-004-dependency-vulnerabilities.md) неизвестен.

## Ограничение окружения

Внешний API заменён заглушкой, написанной для тестирования. Она повторяет контракт из спецификации, но не является настоящей реализацией: в частности, операция удаления отвечает кодом 204, не убирая запись из хранилища. Для проверок, где важно состояние данных после операции, потребуется полноценная реализация API.
